# 后台管理双菜单跳转管理逻辑设计

## 1. 背景与目标

后台管理需要同时支持两套左侧菜单导航：

- **公司管理菜单**：`MenuStatus.CompanyManagement = 1`
- **用户管理菜单 / 个人中心菜单**：`MenuStatus.CompanyPerson = 2`

需要满足以下要求：

1. 用户登录后默认进入 **用户管理菜单 - 用户首页**。
2. 用户可以在 **用户管理菜单** 与 **公司管理菜单** 之间自由切换。
3. 用户在某个菜单模式下按 F5 大刷新后，仍然保持当前菜单模式。
4. 菜单切换后，菜单布局模式不应该被重置，例如展开 / 折叠状态保持不变。
5. 页面进入或刷新后，应正确高亮当前路由对应的菜单项。

本方案围绕当前工程已有代码设计，核心涉及：

| 模块 | 路径 | 职责 |
| --- | --- | --- |
| 菜单基础组件 | `packages/platform/core/ui/src/components/plt-menu` | 负责菜单树渲染、节点高亮、展开收起、路由跳转。 |
| 后台管理导航组件 | `packages/platform/admin-vue/src/views/layout/nav` | 负责展示当前菜单、触发菜单模式切换。 |
| 菜单公共逻辑 | `packages/platform/admin-vue/src/composables/use-menu` | 负责菜单拉取、菜单 URL 格式化、默认菜单计算、模式切换。 |
| 菜单缓存 Store | `packages/platform/admin-vue/src/stores/modules/system-module-access` | 负责缓存当前菜单模式、菜单数据、Tab 数据、KeepAlive 数据。 |
| 路由守卫 | `packages/platform/admin-vue/src/router/tools/guard.ts` | 负责登录态校验、登录后默认跳转、路由同步。 |
| 路由配置 | `packages/platform/admin-vue/src/router/modules/index.ts` | 负责声明公司管理、用户管理相关页面路由。 |

---

## 2. 当前关键现状

### 2.1 菜单类型枚举

当前菜单类型定义在：

```ts
export enum MenuStatus {
  /** 公司管理模式 */
  CompanyManagement = 1,

  /** 公司用户模式 */
  CompanyPerson = 2,
}
```

### 2.2 当前菜单接口数据

菜单接口参数：

```ts
export interface MenuDto {
  navigationType: MenuStatus;
}
```

菜单接口会根据 `navigationType` 返回不同菜单树：

- `navigationType = 2` 返回用户管理菜单，包含 `/user-homepage`、`/notice`。
- `navigationType = 1` 返回公司管理菜单，包含 `/homepage-company`、`/company-user`、`/company-role`。

### 2.3 当前 Store 已有能力

当前 `system-module-access` 已经持久化以下数据到 `sessionStorage`：

```ts
pick: [
  'state.activeTabFullPath',
  'state.tabBarList',
  'state.menuList',
  'state.cachedViewNames',
  'state.navigationType',
]
```

其中 `navigationType` 默认值已经是：

```ts
navigationType: MenuStatus.CompanyPerson
```

这符合“登录后默认进入用户管理菜单”的大方向。

### 2.4 当前菜单组件高亮机制

`plt-menu` 使用以下 props 控制菜单：

```vue
<plt-menu
  :data="menuData"
  :fieldNames="menuProps"
  :default-active="menuDefaultActive"
  :router="true"
/>
```

核心高亮逻辑在 `plt-menu/src/composables/use-tree/index.ts` 中：

- `defaultActive` 变化后，根据 path 匹配菜单节点。
- 找到节点后调用 `setCurrentKey` 设置当前高亮。
- 非折叠模式下自动展开父级。
- 路由模式开启后，点击菜单节点会执行 `router.push(node.path)`。

因此业务侧只要保证传入的 `menuDefaultActive` 与当前路由 `fullPath` 或菜单 URL 一致，就可以正确高亮。

## 3. 总体设计原则

### 3.1 URL 是恢复状态的第一来源，但 URL 不能写死

最终进入业务页面后，菜单 URL 建议携带以下 query：

```text
?menuCode=接口返回值&navigationType=1|2
```

但这里有一个关键原则：**前端不能提前写死 `menuCode`，也不应该写死“用户首页 / 公司首页”的完整跳转地址。**

原因是：

- `menuCode` 属于菜单接口返回的数据，前端在调用菜单接口之前并不知道。
- 默认首页也应该来自菜单接口返回结果，例如“当前模式下第一个可访问菜单”或后端明确标记的默认菜单。
- 前端只应该知道要进入哪一种菜单模式，例如默认进入 `MenuStatus.CompanyPerson`，不应该知道这个模式下首页的 `menuCode` 一定是什么。

因此正确链路是：

```text
确定 navigationType
  -> 调 queryMenuList({ navigationType })
  -> 从返回 trees 中找默认菜单节点
  -> 使用该节点的 url/menuCode/navigationType 动态生成 fullPath
  -> router.push(fullPath)
```

以当前 mock 数据为例，接口返回后动态生成的 URL 可能是：

```text
/user-homepage?menuCode=user-homepage&navigationType=2
/homepage-company?menuCode=homepage-company&navigationType=1
/company-user?menuCode=company-user&navigationType=1
```

这些只能作为“当前 mock 数据下的结果示例”，不能作为实现中的常量。

原因：

1. F5 刷新后，Pinia 会从 `sessionStorage` 恢复，但 URL 仍然是最可靠的当前页面来源。
2. 多菜单模式下，仅通过 path 可能无法判断当前属于哪套菜单；`navigationType` 可以明确当前模式。
3. Tab 去重、菜单高亮、KeepAlive 分组可以复用运行时生成出来的 `menuCode` 与 `navigationType`。

### 3.2 Store 是运行时状态的中心

`system-module-access` 负责维护当前菜单状态：

- 当前菜单模式：`navigationType`
- 当前菜单树：`menuList`
- 当前激活 tab：`activeTabFullPath`
- 当前 tab 列表：`tabBarList`
- 当前 KeepAlive 缓存：`cachedViewNames`

建议后续增强为“按菜单模式分组缓存”，避免两套菜单互相污染：

```ts
export type SystemNavigationOptions = {
  menuList: MenuTreeOptions[];
  tabBarList: TabBarListOptions[];
  cachedViewNames: string[];
};

export type SystemModuleAccessState = {
  /** 当前激活 tab 完整路径 */
  activeTabFullPath: string;

  /** 当前菜单模式 */
  navigationType: MenuStatus;

  /** 公司管理菜单运行时状态 */
  [MenuStatus.CompanyManagement]: SystemNavigationOptions;

  /** 用户管理菜单运行时状态 */
  [MenuStatus.CompanyPerson]: SystemNavigationOptions;
};
```

如果暂时不改分组结构，也至少要保证切换菜单时同时更新：

- `state.navigationType`
- `state.menuList`
- `state.tabBarList`
- `state.activeTabFullPath`
- `state.cachedViewNames`

### 3.3 菜单切换只切业务菜单，不切布局模式

菜单切换按钮只应该切换 `navigationType` 与菜单数据，不应该重置布局相关状态。

例如以下状态不应该由菜单切换逻辑主动修改：

- 左侧栏宽度。
- 左侧栏是否折叠。
- `plt-menu` 的 `collapse` 状态。
- `plt-mobile-container` 的布局尺寸。

如果后续菜单折叠状态需要持久化，应单独放到 layout store，例如：

```ts
layoutStore.state.navCollapsed
layoutStore.state.navWidth
```

不要放在 `system-module-access` 的菜单业务状态中。

## 4. 推荐数据结构

### 4.1 Store State 推荐结构

推荐 `system-module-access/index.type.ts` 中维护如下结构：

```ts
export type SystemNavigationOptions = {
  /** 当前模式下的侧边栏菜单 */
  menuList: MenuTreeOptions[];

  /** 当前模式下的 tab 列表 */
  tabBarList: TabBarListOptions[];

  /** 当前模式下 KeepAlive include 名称 */
  cachedViewNames: string[];
};

export type SystemModuleAccessState = {
  /** 当前激活的 tab fullPath */
  activeTabFullPath: string;

  /** 当前菜单模式 */
  navigationType: MenuStatus;

  /** 公司管理模式缓存 */
  [MenuStatus.CompanyManagement]: SystemNavigationOptions;

  /** 用户管理模式缓存 */
  [MenuStatus.CompanyPerson]: SystemNavigationOptions;
};
```

初始值：

```ts
const createNavigationState = (): SystemNavigationOptions => ({
  menuList: [],
  tabBarList: [],
  cachedViewNames: [],
});

const initialState = (): SystemModuleAccessState => ({
  activeTabFullPath: '',
  navigationType: MenuStatus.CompanyPerson,
  [MenuStatus.CompanyManagement]: createNavigationState(),
  [MenuStatus.CompanyPerson]: createNavigationState(),
});
```

### 4.2 Store Actions 推荐设计

建议 Store 收敛以下 actions，避免各业务组件直接改 state：

| Action | 说明 |
| --- | --- |
| `getNavigationState(navigationType?)` | 获取指定菜单模式的分组状态。 |
| `setNavigationType(navigationType)` | 设置当前菜单模式。 |
| `setMenuList(menuList, navigationType?)` | 设置指定菜单模式的菜单树。 |
| `setTabBarList(tabBarList, navigationType?)` | 设置指定菜单模式的 tab 列表。 |
| `setActiveTab(fullPath)` | 设置当前激活 tab。 |
| `addTab(tab)` | 当前或指定菜单模式下追加 tab，按 `fullPath` 去重。 |
| `removeTab(fullPath, navigationType?)` | 从指定菜单模式移除 tab。 |
| `addCachedView(name, navigationType?)` | 增加 KeepAlive include。 |
| `removeCachedView(name, navigationType?)` | 删除 KeepAlive include。 |
| `clearCachedViews(navigationType?)` | 清空指定菜单模式缓存。 |

示例：

```ts
const getNavigationState = (navigationType = state.navigationType) => {
  return state[navigationType];
};

const setNavigationType = (navigationType: MenuStatus) => {
  state.navigationType = navigationType;
};

const setMenuList = (menuList: MenuTreeOptions[], navigationType = state.navigationType) => {
  state[navigationType].menuList = menuList;
};

const addTab = (tab: TabBarListOptions) => {
  const navigationType = tab.navigationType || state.navigationType;
  const navigationState = getNavigationState(navigationType);

  if (!navigationState.tabBarList.some(item => item.fullPath === tab.fullPath)) {
    navigationState.tabBarList.push(tab);
  }

  state.activeTabFullPath = tab.fullPath;
};
```

### 4.3 持久化建议

为了满足 F5 后保持菜单模式，至少要持久化：

```ts
pick: [
  'state.activeTabFullPath',
  'state.navigationType',
  `state.${MenuStatus.CompanyManagement}`,
  `state.${MenuStatus.CompanyPerson}`,
]
```

如果暂不采用分组结构，则继续持久化当前字段即可：

```ts
pick: [
  'state.activeTabFullPath',
  'state.tabBarList',
  'state.menuList',
  'state.cachedViewNames',
  'state.navigationType',
]
```

但需要注意：非分组结构下，切换菜单会覆盖 `menuList` 与 `tabBarList`，两套菜单不能分别保留 tabs。

## 5. 菜单 URL 设计

### 5.1 格式化规则

菜单接口返回的原始 URL 可能是：

```text
/user-homepage
/homepage-company
/company-user
```

接口同时返回每个节点自己的 `menuCode` 和 `navigationType`。前端格式化 URL 时，不是写死这些值，而是从当前节点上读取：

```ts
node.url
node.menuCode
node.navigationType
```

所以当前 mock 数据格式化后的结果可能是：

```text
/user-homepage?menuCode=user-homepage&navigationType=2
/homepage-company?menuCode=homepage-company&navigationType=1
/company-user?menuCode=company-user&navigationType=1
```

但实现代码里不能写死 `user-homepage`、`homepage-company`、`company-user` 这些值。

推荐封装：

```ts
const formatUrl = (node: MenuTreeOptions): MenuTreeOptions => {
  if (!node.url) return node;

  const urlParams = new URLSearchParams({
    menuCode: node.menuCode,
    navigationType: String(node.navigationType),
  });

  node.url = `${node.url}?${urlParams.toString()}`;
  return node;
};
```

### 5.2 避免重复追加 query

如果菜单数据来自缓存，或者 `formatUrl` 被重复执行，需要避免出现：

```text
/user-homepage?menuCode=user-homepage&navigationType=2?menuCode=user-homepage&navigationType=2
```

更稳妥的写法是先解析原 URL：

```ts
const formatUrl = (node: MenuTreeOptions): MenuTreeOptions => {
  if (!node.url) return node;

  const url = new URL(node.url, window.location.origin);
  url.searchParams.set('menuCode', node.menuCode);
  url.searchParams.set('navigationType', String(node.navigationType));

  node.url = `${url.pathname}${url.search}`;
  return node;
};
```

## 6. 初始化逻辑设计

### 6.1 登录后默认跳转

要求：用户登录后默认进入 **用户管理菜单 - 用户首页**。

这里不能在路由守卫里直接写死：

```ts
const DEFAULT_USER_HOME_PATH = '/user-homepage?menuCode=user-homepage&navigationType=2';
```

因为前端此时并不可靠知道 `menuCode` 是什么，甚至也不应该假设用户首页路径一定是 `/user-homepage`。

推荐改成“先进入默认菜单模式，再由菜单初始化逻辑动态跳转”：

```text
登录成功
  -> router.push('/') 或 router.push({ path: '/', query: { navigationType: MenuStatus.CompanyPerson } })
  -> Main/AppNav 初始化
  -> queryMenuList({ navigationType: MenuStatus.CompanyPerson })
  -> findFirstAvailableMenu(data.trees)
  -> formatUrl(defaultMenu)
  -> router.replace(defaultMenu.url)
```

也就是说，路由守卫最多只负责确定默认模式：

```ts
if (to.path === '/' && accessToken) {
  next({
    path: '/',
    query: {
      navigationType: String(MenuStatus.CompanyPerson),
    },
  });
  return;
}
```

真正的首页地址必须在拿到菜单接口后，由默认菜单节点动态生成。

### 6.2 AppNav 挂载初始化

`nav.ts` 当前挂载后调用：

```ts
await initMenuData({ isChangeNavigation: false });
```

推荐初始化步骤：

1. 读取当前路由 query 中的 `navigationType`。
2. 如果 URL 中有合法 `navigationType`，优先使用 URL 中的值。
3. 如果 URL 中没有，则使用 store 中持久化的 `navigationType`。
4. 如果 store 中也没有，则使用默认值 `MenuStatus.CompanyPerson`。
5. 按最终 `navigationType` 拉取菜单数据。
6. 格式化菜单 URL。
7. 写入 Store。
8. 根据当前路由设置菜单高亮。
9. 如果当前路由不在当前菜单中，则跳转当前模式的默认菜单。

伪代码：

```ts
const resolveNavigationType = () => {
  const queryNavigationType = Number(route.query.navigationType);

  if ([MenuStatus.CompanyManagement, MenuStatus.CompanyPerson].includes(queryNavigationType)) {
    return queryNavigationType as MenuStatus;
  }

  return systemModuleAccess.state.navigationType || MenuStatus.CompanyPerson;
};

const initMenuData = async ({ isChangeNavigation = false }) => {
  const targetNavigationType = isChangeNavigation
    ? getOppositeNavigationType(systemModuleAccess.state.navigationType)
    : resolveNavigationType();

  systemModuleAccess.setNavigationType(targetNavigationType);

  const { data } = await queryMenuList({ navigationType: targetNavigationType });

  const menuList = updateTreeNodeForTree({
    treeNode: data.trees,
    updateNode: formatUrl,
  }) || [];

  systemModuleAccess.setMenuList(menuList, targetNavigationType);

  const defaultMenu = findFirstAvailableMenu(menuList);
  const activeMenu = findMenuByFullPath(menuList, route.fullPath) || defaultMenu;

  menuDefaultActive.value = activeMenu?.url || '';

  if (isChangeNavigation && defaultMenu) {
    await enterMenu(defaultMenu, targetNavigationType);
  }
};
```

## 7. 菜单切换逻辑设计

### 7.1 切换入口

当前切换入口在：

```vue
<div class="nav-foot" @click="initMenuData({ isChangeNavigation: true })">
  {{ menuModelTitle }}
</div>
```

建议保留该入口，但命名上更明确：

```vue
<div class="nav-foot" @click="switchNavigationType">
  {{ switchMenuTitle }}
</div>
```

其中：

- 当前是用户管理菜单时，按钮文案显示“公司管理”。
- 当前是公司管理菜单时，按钮文案显示“个人中心”或“用户管理”。

### 7.2 切换流程

菜单切换时建议执行以下流程：

```text
用户点击切换按钮
        │
        ▼
计算目标 navigationType
        │
        ▼
拉取目标菜单数据 queryMenuList({ navigationType: targetType })
        │
        ▼
格式化菜单 URL，补齐 menuCode/navigationType
        │
        ▼
写入 Store：navigationType + menuList
        │
        ▼
找到目标菜单第一项可访问菜单
        │
        ▼
创建默认 affix tab
        │
        ▼
更新 activeTabFullPath、tabBarList、menuDefaultActive
        │
        ▼
router.push(defaultMenu.url)
        │
        ▼
plt-menu 根据 defaultActive 高亮目标菜单项
```

### 7.3 切换后是否保留 Tab

这里有两种策略。

#### 方案 A：切换菜单后进入目标模式默认菜单，只保留目标默认菜单 Tab

这是最简单、最符合“菜单模式切换”的方案。

注意：这里说的“默认菜单”不是前端写死的 `/homepage-company` 或 `/user-homepage`，而是目标菜单接口返回后，通过规则找出来的菜单节点。

推荐默认菜单规则优先级：

```text
后端明确标记的默认菜单
  > 当前菜单树第一个有 url 的菜单节点
```

当前接口还没有默认标记时，可以先使用已有的：

```ts
findFirstAvailableMenu(menuList)
```

切换到公司管理时：

```text
queryMenuList({ navigationType: MenuStatus.CompanyManagement })
  -> findFirstAvailableMenu(companyMenuList)
  -> router.push(defaultMenu.url)
```

切换到用户管理时：

```text
queryMenuList({ navigationType: MenuStatus.CompanyPerson })
  -> findFirstAvailableMenu(userMenuList)
  -> router.push(defaultMenu.url)
```

优点：

- 行为清晰。
- 不会出现跨菜单模式 tab 混乱。
- 不依赖前端硬编码 `menuCode` 或首页 path。
- 实现成本低。

缺点：

- 用户切回旧模式时，旧模式打开过的 tabs 不保留。

#### 方案 B：按菜单模式分别保留 Tab

切换菜单时：

- 进入目标模式上一次激活的 tab。
- 如果目标模式没有 tab，则进入目标模式首页。

优点：

- 用户体验更好。
- F5 与来回切换都能恢复上下文。

缺点：

- 需要 Store 按 `navigationType` 分组保存 `tabBarList`、`cachedViewNames`。

推荐：**如果当前只是完成基础需求，先采用方案 A；如果 TabBar 已经准备完善，建议直接采用方案 B。**

## 8. F5 刷新恢复逻辑

### 8.1 刷新场景

用户在以下地址刷新：

```text
/company-user?menuCode=company-user&navigationType=1
```

刷新后应该保持：

- 当前菜单模式：公司管理菜单。
- 左侧展示公司管理菜单列表。
- 当前高亮：公司用户。
- Tab 激活项：公司用户。

用户在以下地址刷新：

```text
/notice?menuCode=notice&navigationType=2
```

刷新后应该保持：

- 当前菜单模式：用户管理菜单。
- 左侧展示用户管理菜单列表。
- 当前高亮：通知。
- Tab 激活项：通知。

### 8.2 恢复优先级

刷新恢复时，建议优先级为：

```text
route.query.navigationType
  > sessionStorage 中的 state.navigationType
  > 默认 MenuStatus.CompanyPerson
```

原因：

- URL 表示用户当前真正访问的页面。
- sessionStorage 表示上一次运行时状态。
- 默认值只兜底第一次登录或异常场景。

### 8.3 当前代码需要注意的问题

当前 `use-menu.ts` 中切换菜单时已经计算了 `type`：

```ts
let type = navigationType.value;
if (isChangeNavigation) {
  type = navigationType.value === MenuStatus.CompanyManagement
    ? MenuStatus.CompanyPerson
    : MenuStatus.CompanyManagement;
}
```

但接口请求参数当前使用的是：

```ts
const params = {
  navigationType: navigationType.value,
};
```

这里在切换菜单时会请求旧菜单，应该改成：

```ts
const params = {
  navigationType: type,
};
```

否则点击切换时，Store 里的 `navigationType` 可能变成目标模式，但菜单数据还是旧模式，导致刷新、高亮、Tab 都容易错乱。

## 9. 默认高亮菜单项设计

### 9.1 高亮来源

菜单高亮应该优先使用当前路由：

```ts
menuDefaultActive.value = route.fullPath;
```

如果当前路由没有匹配到菜单，再使用当前模式默认菜单：

```ts
menuDefaultActive.value = defaultMenu.url;
```

### 9.2 匹配规则

由于业务菜单 URL 已经带 query，所以高亮应按完整 URL 匹配：

```text
route.fullPath === menu.url
```

如果有一些业务参数不参与菜单匹配，例如：

- `noticeId`
- `customParameters`

当前 `plt-menu` 已经支持忽略部分参数：

```ts
const ignoreParams = ['customParameters', 'noticeId'];
```

这可以保留。

### 9.3 推荐处理流程

```ts
const currentMenu = findMenuByUrl(currentMenuList.value, route.fullPath);

if (currentMenu) {
  menuDefaultActive.value = route.fullPath;
} else {
  menuDefaultActive.value = defaultMenu?.url || '';
}
```

### 9.4 点击菜单后的高亮

`plt-menu` 开启 `router` 后，点击菜单节点会自动：

1. 执行 `router.push(node.path)`。
2. 设置当前菜单节点高亮。
3. 触发 `node-click` 和 `current-change`。

业务侧不需要在 `handleNodeClick` 中重复 `router.push`。

## 10. TabBar 与路由同步设计

### 10.1 路由同步时机

建议在路由守卫 `afterEach` 中启用：

```ts
syncRouteToTab(to);
```

当前代码里该逻辑被注释：

```ts
// syncRouteToTab(to);
```

后续如果要让 TabBar 跟随路由变化，需要打开。

### 10.2 Tab 创建规则

从路由创建 Tab 时，应读取：

- `route.fullPath` 作为唯一 key。
- `route.query.menuCode` 查找菜单标题、图标。
- `route.query.navigationType` 判断属于哪套菜单。
- `route.meta.title` 作为兜底标题。
- `route.meta.customizeOps.keepAlive` 判断是否 KeepAlive。

推荐结构：

```ts
const createTabFromRoute = (route: RouteLocationNormalizedLoaded): TabBarListOptions => {
  const navigationType = Number(route.query.navigationType || systemModuleAccess.state.navigationType) as MenuStatus;
  const menuCode = String(route.query.menuCode || '');
  const menu = findMenuByCode(systemModuleAccess.getNavigationState(navigationType).menuList, menuCode);

  return {
    title: menu?.menuName || String(route.meta.title || route.name || route.path),
    path: route.fullPath,
    fullPath: route.fullPath,
    routeName: route.name ? String(route.name) : undefined,
    menuCode,
    navigationType,
    icon: menu?.menuSvgId,
    affix: !!customizeOps.affix,
    closable: !customizeOps.affix,
    keepAlive: !!customizeOps.keepAlive,
    componentName: route.name ? String(route.name) : undefined,
  };
};
```

### 10.3 当前代码需要注意的问题

当前 `use-tab-bar-route-sync.ts` 中读取的是：

```ts
systemModuleAccess.state.menulist
```

但当前 Store 类型中字段是：

```ts
menuList
```

大小写和名称不一致，需要统一，否则会导致找不到菜单。

当前 `tabs-bar.ts` 中读取的是：

```ts
const barsList = computed(() => systemModuleAccess.state.tabBarlist);
```

但 Store 字段是：

```ts
tabBarList
```

也需要统一为 `tabBarList`。

## 11. KeepAlive 缓存设计

### 11.1 设计目标

不同菜单模式下的页面缓存应该互相隔离。

例如：

- 用户管理菜单缓存：`user-homepage`、`notice`
- 公司管理菜单缓存：`homepage-company`、`company-user`

切换模式后，`KeepAlive include` 应该读取当前 `navigationType` 对应的缓存列表。

### 11.2 Main 组件读取方式

当前 `main.ts` 中：

```ts
const cachedViewNames = computed(() => {
  const navigationType = systemModuleAccess.state.navigationType;
  return [];
});
```

推荐改成：

```ts
const cachedViewNames = computed(() => {
  return systemModuleAccess.getNavigationState().cachedViewNames;
});
```

如果暂不做分组结构，则至少返回：

```ts
const cachedViewNames = computed(() => systemModuleAccess.state.cachedViewNames);
```

## 14. 关键伪代码汇总

### 14.1 useMenu 推荐核心实现

```ts
export const useMenu = () => {
  const router = useRouter();
  const route = useRoute();
  const systemModuleAccess = systemModuleAccessStore();

  const currentMenuList = ref<MenuTreeOptions[]>([]);
  const menuDefaultActive = ref('');

  const getOppositeNavigationType = (type: MenuStatus) => {
    return type === MenuStatus.CompanyManagement
      ? MenuStatus.CompanyPerson
      : MenuStatus.CompanyManagement;
  };

  const resolveNavigationType = () => {
    const queryNavigationType = Number(route.query.navigationType);
    const validTypes = [MenuStatus.CompanyManagement, MenuStatus.CompanyPerson];

    if (validTypes.includes(queryNavigationType)) {
      return queryNavigationType as MenuStatus;
    }

    return systemModuleAccess.state.navigationType || MenuStatus.CompanyPerson;
  };

  const initMenuData = async ({ isChangeNavigation = false }) => {
    const targetNavigationType = isChangeNavigation
      ? getOppositeNavigationType(systemModuleAccess.state.navigationType)
      : resolveNavigationType();

    const { data } = await queryMenuList({ navigationType: targetNavigationType });

    const menuList = updateTreeNodeForTree({
      treeNode: data.trees,
      updateNode: formatUrl,
    }) || [];

    currentMenuList.value = menuList;
    systemModuleAccess.setNavigationType(targetNavigationType);
    systemModuleAccess.setMenuList(menuList, targetNavigationType);

    const defaultMenu = findFirstAvailableMenu(menuList);
    const currentMenu = findMenuByUrl(menuList, route.fullPath);
    const activeMenu = currentMenu || defaultMenu;

    menuDefaultActive.value = activeMenu?.url || '';

    // 切换菜单、首次进入 /、或者当前路由不属于目标菜单时，都跳转到接口返回的默认菜单
    const shouldEnterDefaultMenu = isChangeNavigation || route.path === '/' || !currentMenu;

    if (shouldEnterDefaultMenu && defaultMenu) {
      const homeTab = createTabByMenu(defaultMenu);
      systemModuleAccess.setTabBarList([homeTab], targetNavigationType);
      systemModuleAccess.setActiveTab(homeTab.fullPath);

      if (route.path === '/') {
        await router.replace(defaultMenu.url);
      } else {
        await router.push(defaultMenu.url);
      }
    }
  };

  return {
    currentMenuList,
    menuDefaultActive,
    initMenuData,
  };
};
```

### 14.2 findMenuByUrl

```ts
const findMenuByUrl = (menus: MenuTreeOptions[], url?: string): MenuTreeOptions | undefined => {
  if (!url) return;

  for (const menu of menus) {
    if (menu.url === url) return menu;

    const child = findMenuByUrl(menu.children || [], url);
    if (child) return child;
  }
};
```

### 14.3 createTabByMenu

```ts
const createTabByMenu = (menu: MenuTreeOptions): TabBarListOptions => ({
  title: menu.menuName,
  path: menu.url,
  fullPath: menu.url,
  menuCode: menu.menuCode,
  navigationType: menu.navigationType,
  icon: menu.menuSvgId,
  affix: true,
  closable: false,
});
```

## 16. 最终推荐结论

1. **菜单模式以 `navigationType` 为核心状态。**
   - `1` 表示公司管理。
   - `2` 表示用户管理。

2. **运行时生成的菜单 URL 应携带 `menuCode` 与 `navigationType`。**
   - `menuCode` 来自菜单接口返回的节点数据，前端不能提前写死。
   - 这是刷新恢复、菜单高亮、Tab 同步的关键。

3. **初始化时优先读取 URL 的 `navigationType`。**
   - 保证 F5 后能恢复当前菜单模式。

4. **切换菜单时必须请求目标 `navigationType` 的菜单。**
   - 当前代码需要把请求参数从 `navigationType.value` 修正为计算后的 `type`。

5. **切换菜单后必须跳转目标菜单默认页。**
   - 默认页必须从接口返回的菜单树中动态计算。
   - 不能在前端写死 `/homepage-company?...` 或 `/user-homepage?...`。

6. **菜单高亮以当前 `route.fullPath` 为优先。**
   - 匹配不到再回退到当前模式默认菜单。

7. **菜单业务状态和布局状态分离。**
   - 切换菜单不应该重置折叠模式、侧栏宽度等布局状态。

8. **中长期建议 Store 按 `navigationType` 分组缓存。**
   - 分别保存公司管理和用户管理的 `menuList`、`tabBarList`、`cachedViewNames`。
   - 这样切换、刷新、Tab、KeepAlive 的边界最清晰。
